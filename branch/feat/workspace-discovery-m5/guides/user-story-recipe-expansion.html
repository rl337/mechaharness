Litmus (corrected)

If a persona claim is a valid MechaHarness user story, there must be an execution graph (Agentic Recipe + runners + DI seams) that can carry it, and a CLI/user_story walk that exercises that graph.

  • Missing path ⇒ expand inventory (RagRetriever + context_pack was the model).

  • Do not demote a valid story to unit-only because the graph is unfinished.

  • Unit/doctest still covers helpers; stories own the product walk.

Yes, selectively — not a rewrite of everything.

Working groups (recipe-first)

Work each group by: name/extend recipe → runners + DI → restore/migrate stories → regenerate guide → green checks.

G3 — Access / authority as graph gates

Not a grab-bag of probes: recipes or durable envelopes that deny/narrow on the product path (capability envelope, auth epoch resume, soft vs hard, approval interrupt). Former P5.

G4 — Graph executor / budget / resume

Durable + budget recipes; migrate P8 probes onto start/answer or run_recipe with real budget/effect runners. TDR stays; align crash stories with the same façade where practical.

G5 — Eval / research packs

Taloneth P7: prefer eval recipes / export graphs over probe bags (policy_replay, shadow compare, eval matrix). Compose with G0 shadow/telemetry.

G6 — Recipe lifecycle (recipe_plan)

Keep recipe_plan for evolution/port/compose if the claim is registry lifecycle. When the claim is “run the evolved recipe,” promote to execute (G1). Do not invent another *_case bag.

G7 — Diagnostics that stay thin verbs

Replay / routing / parity / affinity may remain one-shot verbs (like infer) when they are not subgraph control stories. Still need honest narratives and cassettes; no probe wrapper.

Anti-patterns (do not repeat)

  1. *_case product verbs that dispatch on case: with baked answers.

  2. Marking a story green for instantiate_recipe alone when the inspiration claim is an outcome of running the recipe.

  3. Demoting a persona claim to unit tests because runners are missing.

  4. Migrating probe → user_story before the graph exists (YAML churn without product path).

Suggested order

  1. G0 — restore four plane stories (blocks honesty of P3).

  2. G1 — verify_repair / bounded_retry execute (high reuse).

  3. G3 or G4 — whichever unblocks more P5/P8 hosts.

  4. G2 deepen RAG; G5 eval; G6 lifecycle plans as needed.
